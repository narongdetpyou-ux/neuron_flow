# สกุลเงินและจำนวนตำแหน่งทศนิยม

รุ่น 0.3.0 รองรับ 46 สกุลเงินสำหรับ CSV และ invoice JSON โดยยังใช้
standard library ไม่มี dependency, API key หรือบริการอัตราแลกเปลี่ยนเพิ่ม
ความสามารถนี้ไม่มีในไฟล์ Release 0.2.1 ที่เผยแพร่ก่อนหน้า

## รหัสที่รองรับ

ใช้รหัส ISO 4217 ตัวพิมพ์ใหญ่ตรงตัว เช่น `USD` ไม่ใช้สัญลักษณ์ `$` หรือ `¥`
ไม่ตัดช่องว่างหรือแปลงตัวพิมพ์ให้อัตโนมัติ ค่า `usd`, ` USD`, `XXX` หรือ `BTC`
ถูกปฏิเสธ รายการนี้เป็นขอบเขตที่โปรแกรมรองรับ ไม่ใช่รายชื่อทุกสกุลเงินทั่วโลก
ตารางใน [currencies.py](../neuron_flow/currencies.py) เป็นแหล่งกำหนดกติกาของโปรแกรม

| ตำแหน่งทศนิยมสูงสุด | รหัสสกุลเงิน |
| --- | --- |
| 0 | CLP, ISK, JPY, KRW, VND |
| 2 | AED, AUD, BDT, BGN, BRL, CAD, CHF, CNY, CZK, DKK, EGP, EUR, GBP, HKD, HUF, IDR, ILS, INR, MXN, MYR, NOK, NZD, PHP, PKR, PLN, QAR, RON, RUB, SAR, SEK, SGD, THB, TRY, TWD, USD, ZAR |
| 3 | BHD, JOD, KWD, OMR, TND |

จำนวนตำแหน่งนี้ใช้กับหน่วยย่อยทางบัญชีตาม ISO 4217 ไม่ใช่กติกาปัดเศษเงินสดของแต่ละประเทศ

## กติกาของยอดเงิน

`unit_price` และ `declared_total` ใช้ข้อความตัวเลข ASCII ไม่ติดลบ อนุญาตจำนวนเต็ม
และทศนิยมไม่เกินจำนวนตำแหน่งของสกุลนั้น ไม่รองรับเครื่องหมายบวก/ลบ เครื่องหมายคั่นหลัก
หรือรูปแบบ exponent เช่น `1e2` ราคาต่อหน่วยสูงสุด 10¹² และยอดที่ระบุสูงสุด 10²²
เป็นจำนวนในสกุลของเอกสารนั้น จำนวนซื้อยังเป็นจำนวนเต็ม 1–1,000,000

ระบบปฏิเสธความละเอียดเกินกติกาโดยไม่ปัดเศษ เช่น USD `1.001`, JPY `1.0` และ KWD
`1.0001` แม้หลักที่เกินจะเป็นศูนย์ก็ตาม ผลคำนวณใช้รูปแบบคงที่ตามสกุล:

| สกุล | ราคา × จำนวน | ผลคำนวณ |
| --- | --- | --- |
| USD | `10.75` × 2 | `21.50` |
| EUR | `8.50` × 3 | `25.50` |
| JPY | `500` × 3 | `1500` |
| KWD | `1.234` × 3 | `3.702` |

คำนวณด้วย Decimal และตรวจซ้ำแยกด้วย integer หน่วยย่อย เช่น เซนต์ เยน หรือฟิลส์
ไม่มีการใช้ float สำหรับยอดเงิน `difference` ยังเป็นยอดคำนวณลบยอดที่ระบุ
และใช้จำนวนตำแหน่งเดียวกับสกุลของเอกสาร

## เอกสารและยอดรวม batch

ทุกแถวใน `document_id` เดียวกันต้องใช้สกุลเดียวกัน การใส่ USD กับ EUR ในใบเดียวกัน
ได้ `CURRENCY_CONFLICT` และสถานะ INVALID ส่วนหลายเอกสารใน batch เดียวกันใช้ต่างสกุลได้
เอกสารที่มีสกุลผสมหรือไม่รองรับไม่มีสกุลและยอดที่รับรอง ผล `currency` เป็น `null`

รันตัวอย่างจาก root ของ checkout:

```bash
python -m neuron_flow csv examples/purchases_international.csv --batch-id international --workspace batch_workspace
python -m neuron_flow batch-resume international --workspace batch_workspace
```

ได้ 4 VALID และยอดรวมดังนี้:

```json
{
  "currency": null,
  "certified_total": null,
  "certified_totals": {
    "EUR": "25.50",
    "JPY": "1500",
    "KWD": "3.702",
    "USD": "21.50"
  }
}
```

`certified_totals` นับเฉพาะเอกสาร VALID แยกตามสกุลที่ระบุได้แน่นอนจาก source
หากสกุลหนึ่งมีแต่เอกสาร INVALID หรือ ERROR ยอดของสกุลนั้นเป็นศูนย์ตามรูปแบบของสกุล
เอกสารที่ระบุสกุลไม่ได้ไม่สร้างช่องยอดรวม เมื่อมีสกุลเดียว `currency` และ
`certified_total` แสดงรหัสกับยอดของสกุลนั้นเพิ่มเติม เมื่อมีหลายสกุลหรือไม่มีสกุลที่ระบุได้
สองช่องนี้เป็น `null` ไม่มีการรวมยอดต่างสกุล ไม่มีการแปลงเงินหรือดึงอัตราแลกเปลี่ยน

ผลเอกสารใน `details.json` และแถวของ `summary.csv` ภายใต้สัญญาหลายสกุลเงินมี
ช่อง `currency` เพิ่ม รายงานตรวจรูปแบบทศนิยม สกุล ยอดจาก source และ SHA-256 ก่อนส่งมอบ
`source.csv` ยังเก็บไบต์ต้นทางเดิม การเปิดต่อไม่เขียนผลที่ส่งมอบแล้วซ้ำ

## ความเข้ากันได้กับงานเดิม

ข้อมูล THB ล้วนยังใช้ `purchase-csv-v1` พร้อมรูปแบบรายงานเดิม ข้อมูลใหม่ที่มีสกุลอื่น
เลือก `purchase-csv-multicurrency-v1` อัตโนมัติ งาน v1 ที่บันทึกไว้เปิดต่อด้วยกติกาเดิม
จึงไม่เปลี่ยนผลเดิมของ USD ที่เคย INVALID ให้เป็น VALID ระหว่างการกู้คืน
หากรับ source เดิมภายใต้สัญญาใหม่ ให้ใช้ batch ID ใหม่

fixture 100 เอกสารใน `acceptance/` และหลักฐานประวัติไม่ถูกแก้ไข ผล 80 VALID / 20 INVALID
เป็นผลภายใต้สัญญา v1 ซึ่งตั้งใจไม่รองรับ USD ใช้ `BatchRuntime(..., legacy_thb=True)`
เพื่อ replay fixture ด้วยกติกาเดิม เมื่อประมวลผลด้วยสัญญาใหม่ เอกสาร USD ในนั้นสามารถผ่านได้
การตรวจ API ระดับเอกสารหรือ workflow เดิมใช้ `validate_document(..., multicurrency=False)`
หรือ `csv_workflow(..., multicurrency=False)` ตามลำดับ

สำหรับ Python API ใหม่ `validate_document` และ `csv_workflow` เปิดรองรับหลายสกุลเงิน
เป็นค่าเริ่มต้น ดู [คู่มือ Python API](PYTHON_API_TH.md) โค้ดที่อ่าน CSV report ต้องตรวจ
`contract_version` ก่อนสมมติรูปแบบคอลัมน์หรือใช้ `certified_total` เป็นยอดเดียวเสมอ

invoice JSON ผ่าน `Runtime.ingest` ใช้ Agent รุ่น `2` สำหรับ extract, calculate และ verify
เพราะกติกาสกุลเงินและทศนิยมเปลี่ยนจากเดิม งาน invoice JSON ที่บันทึกด้วย Agent รุ่น `1`
ต้องใช้ runtime เดิมเพื่อเปิดต่อ หรือเริ่มงานใหม่ใน workspace ใหม่ Runtime จะปฏิเสธ
Agent version ที่ไม่ตรงกัน ส่วน echo ยังคงรุ่น `1` และ CSV Agents ยังคงรุ่น `0.2.0`
โดยแยกกติกาใหม่ด้วย contract และ workflow params
