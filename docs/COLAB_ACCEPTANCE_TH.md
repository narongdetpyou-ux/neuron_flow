# ตรวจรับ Neuron Flow บน Google Colab จริง

**สถานะ ณ จัดทำเอกสาร: `not_run`** สภาพแวดล้อมพัฒนานี้ไม่มี Colab runtime ให้ตรวจจริง
เอกสารนี้เป็นรายการที่จะตรวจ ไม่ใช่รายงานว่าผ่านแล้ว การตรวจ syntax การจำลองในเครื่อง
การ import `google.colab` หรือการอนุมัติเผยแพร่ใช้แทนหลักฐานการใช้งานจริงไม่ได้

ให้ตรวจรุ่นเผยแพร่ **0.2.0 ก่อน** เพื่อบันทึกฐานการใช้งาน Colab ที่ยังขาดอยู่ จากนั้นตรวจ
**candidate 0.2.1** แยกอีกรอบเมื่อชุดไฟล์และคำสั่งรุ่นใหม่พร้อม 0.2.1 ยังไม่ได้รับอนุมัติเผยแพร่
อย่าแก้ผลตรวจย้อนหลังของ 0.2.0 หรือคำตอบอ้างอิงเพื่อให้ผลใหม่ดูเหมือนผ่าน

## 1. ระบุชุดไฟล์และเริ่ม runtime ใหม่

- บันทึกรุ่น Git commit/tag ชื่อ ZIP และ SHA-256 ของ ZIP ที่จะตรวจ เลือกชุดไฟล์ของรุ่นนั้นจริง
  เช่น `neuron_flow_v0.2.0.zip` พร้อมไฟล์ `.sha256`; 0.2.1 ใช้ ZIP ของ candidate ที่ระบุแน่นอน
- เริ่ม Colab runtime ใหม่ บันทึกเวลา UTC รุ่น Python ข้อมูล runtime และระบบปฏิบัติการที่สังเกตได้จริง
- เปิด Notebook ที่มากับ ZIP รุ่นเดียวกัน อัปโหลด ZIP เพียงไฟล์เดียว ตรวจ SHA-256 ของ ZIP
  เทียบกับค่าที่บันทึก และตรวจทุกไฟล์ภายในด้วย `SHA256SUMS.txt` ก่อนรันโค้ด
- บันทึกว่า `PROJECT` และ `WORKSPACE` ชี้ตำแหน่งใด รุ่น 0.2.0 ใช้
  `/content/neuron_flow_project/neuron_flow` และ `/content/neuron_flow_workspace`

**ผ่านเมื่อ:** ระบุชุดไฟล์ที่จะทำซ้ำได้ครบ hash ตรง และใช้ runtime ใหม่จริง
เก็บ stdout/stderr ของแต่ละคำสั่งและ exit code พร้อมเวลาเริ่ม/จบ

## 2. อัปโหลด CSV และตรวจยอดอ้างอิง

- อัปโหลด `acceptance/input.csv` จากแพ็กเกจที่ตรวจ บันทึก hash ต้นทาง และรันตาม Notebook
- ตรวจครบ 100 เอกสาร ได้ 80 VALID / 20 INVALID / 0 ERROR และเทียบผลรายใบทุกช่องกับ
  `acceptance/expected_results.json` ที่ล็อกไว้ ไม่ใช้เพียงตัวเลขจำนวนเอกสารสรุป
- ตรวจตัวอย่างปกติ ตัวอย่างข้อมูลผิด UTF-8 BOM ข้อความหลายบรรทัด และแถวที่ไม่มี `document_id`
  แยกเก็บข้อมูลเข้าและผลจริงของแต่ละกรณี ตรวจว่าไม่มีแถวหายหรือถูกจัดกลุ่มซ้ำ
- เปิด `summary.csv`, `details.json`, `source.csv` ตรวจ SHA-256 และขนาดจาก receipt
  ย้อนจาก source_rows ถึง record ต้นทางได้ ค่าเงินตรงทุกสตางค์ และยอดที่รับรองนับเฉพาะ VALID
- รัน verifier ตาม README ของรุ่นนั้น เก็บจำนวน baseline/new tests, failures, errors และ skipped
  **จากรายงานที่รันจริง** ไม่กรอกจำนวนชุดใหม่ตามรุ่นเก่า เพราะ 0.2.1 จะเพิ่มกรณีตรวจ

**ผ่านเมื่อ:** ผลเอกสารตรงคำตอบที่ล็อกทั้งหมด รายงานย้อนกลับได้ และการตรวจที่กำหนดผ่านจริง
แยกจำนวนเอกสาร 100 ใบออกจากจำนวน test cases ในรายงานเสมอ

## 3. เปิดงานเดิมต่อโดยไม่อัปโหลด CSV ซ้ำ

- ก่อนเปิดต่อ เก็บ snapshot ของสถานะรายขั้น จำนวน attempts และประวัติงาน
  รวม hash/ขนาด/mtime ของรายงานที่สำเร็จแล้ว
- เรียก `batch-resume` โดยใช้ batch_id และ workspace เดิม ไม่อัปโหลด CSV ใหม่
- เก็บ snapshot หลังเปิดต่อ แล้วเปรียบเทียบจำนวนเอกสาร ยอดเงิน สถานะ attempts และประวัติ
  รายงานเดิมต้องมี bytes/hash/mtime เดิม ขั้นที่สำเร็จต้องไม่ถูกรันซ้ำ

**ผ่านเมื่อ:** ใช้ผลสำเร็จเดิม รายงานไม่ถูกสร้างซ้ำ และการเปิดต่อไม่เพิ่ม attempts ของขั้นที่สำเร็จ
หากมี ERROR ต้องยังปรากฏชัด ไม่ถือว่าการเขียนรายงานได้ทำให้ ERROR หายไป

## 4. ตรวจการหา batch และหยุด controller สำหรับ candidate 0.2.1

ส่วนนี้เป็นเกณฑ์ของคำสั่งใหม่ใน **0.2.1 เมื่อ implementation พร้อม** ไม่ใช่คำสั่งของ 0.2.0
ตัวอย่างต่อไปนี้รันจากโฟลเดอร์ PROJECT:

```bash
python -m neuron_flow csv acceptance/input.csv --submit-only --workspace /content/neuron_flow_workspace
python -m neuron_flow batch-list --workspace /content/neuron_flow_workspace
python -m neuron_flow batch-resume <batch_id> --workspace /content/neuron_flow_workspace
```

- `--submit-only` ต้องบันทึกงานและคืน batch_id ก่อนเริ่ม Agent เก็บผลรับงานเพื่อใช้ทำต่อ
  ทดสอบด้วยว่าเมื่อไม่มีผล CLI/session metadata ให้ใช้ `batch-list` ค้นงานเดิมจาก workspace ได้
- เปิด `batch-resume` ใน controller ที่ควบคุมได้ ระบุ PID ของ controller และเก็บ log ของตนเอง
  เรียก `batch-list` ขณะ controller ยังทำงาน คำสั่งต้องอ่านสถานะได้โดยไม่ยึด controller lock
- หยุด controller ที่ระบุไว้ก่อนคืนผล CLI สุดท้าย เก็บสถานะก่อนหยุดและหลักฐานการหยุดจริง
  ใช้ `batch-list` ค้นงาน แล้วเปิดต่อด้วย batch_id ที่พบ
- เปรียบเทียบขั้นที่สำเร็จก่อนหยุดกับผลหลังเปิดต่อ ขั้นเหล่านั้นต้องไม่ทำซ้ำ;
  ความพยายามที่ถูกขัดจังหวะนับอยู่ในงบรวมไม่เกิน 2 ครั้ง
- ตรวจว่า `batch-list` ไม่สร้างงาน/ตาราง/ไฟล์ฐานข้อมูลใหม่ ไม่เปลี่ยน attempts หรือเพิ่ม event
  เมื่อไม่มี writer สถานะและไฟล์ต้องไม่เปลี่ยนเพราะการอ่าน; ขณะมี writer ให้แยกการเปลี่ยนจาก controller
  ออกจากคำสั่งอ่าน ไม่ใช้ hash ฐานข้อมูลที่กำลังถูกเขียนเป็นเงื่อนไขว่าต้องคงเดิม

**ผ่านเมื่อ:** หางานและทำต่อได้แม้ไม่เคยได้รับผล CLI สุดท้าย คำสั่งอ่านไม่เปลี่ยนงาน
เอกสารอื่นยังจบได้ และหลักฐานบอกได้ว่าขั้นใดทำต่อหรือใช้ผลเดิม

## 5. ดาวน์โหลดและคืน backup ใน runtime ใหม่

- รอ controller/CLI จบก่อนสำรอง SQLite ด้วย backup API ตาม Notebook
  backup ต้องรวม workspace รายงาน verification และ session metadata พร้อม hash manifest
- บันทึกชื่อ ZIP สำรอง ขนาด SHA-256 และเวลาที่เรียกดาวน์โหลด จากนั้นตรวจว่าไฟล์ปรากฏ
  ในเครื่องผู้ใช้จริงและ hash ตรง บันทึกคำยืนยันว่าได้รับไฟล์พร้อมเวลาและผู้ตรวจ
  การเรียก `files.download` หรือมีไฟล์อยู่ใน `/content` อย่างเดียวยังไม่ผ่านข้อนี้
- เริ่ม **runtime ใหม่อีกครั้ง** อัปโหลด ZIP โปรเจกต์เดิมและ backup ที่ได้รับจริง
  คืน workspace ด้วยรุ่นเดียวกันที่ path เดิม เนื่องจาก receipt เก็บ absolute path
- ไม่อัปโหลด CSV ซ้ำ เรียกสถานะ/เปิดต่อ แล้วเปรียบเทียบผลเอกสาร attempts ประวัติ
  และ hash รายงานกับ snapshot ก่อนสำรอง
- ทดสอบว่าการคืนทับ workspace ที่มีข้อมูลอยู่ถูกปฏิเสธ โดยรักษาข้อมูลเดิม

**ผ่านเมื่อ:** ยืนยันการรับไฟล์จริง คืน backup ข้าม runtime ได้โดยไม่มี CSV ต้นทางใหม่
และผลสำเร็จเดิมไม่ถูกรันหรือเขียนซ้ำ

## 6. ตรวจความเข้ากันได้ 0.2.0 → 0.2.1 แยกจากการคืนรุ่นเดิม

ใช้ **สำเนา** workspace 0.2.0 ที่ตรวจในข้อก่อนหน้า รักษาต้นฉบับและหลักฐานเดิมไว้
ทดสอบ candidate 0.2.1 ตามวิธีสลับโปรเจกต์/คืน workspace ที่กำหนดใน README ของ candidate
โดยยังรักษา path ของ workspace ให้ตรง receipt เดิม

- อ่านรายการ/สถานะและเปิดงาน 0.2.0 เดิมด้วย 0.2.1 ได้ภายใน compatibility policy ที่ประกาศ
- ผลเก่าต้องยังบอกว่าเกิดจาก 0.2.0 ไม่แก้รุ่นย้อนหลังใน frozen payload หรือแก้ receipt เพื่อให้ผ่าน
- ข้อมูลเดิมและรหัสเดิมใช้ผลสำเร็จเดิม hash/attempts/history ไม่เปลี่ยน
  งานใหม่ที่สร้างด้วย candidate ต้องบันทึกรุ่น 0.2.1 ตามจริง
- contract, Agent version หรือข้อมูลต้นทางที่เปลี่ยนนอก policy ต้องเกิด conflict และรักษาผลเดิม

**ผ่านเมื่อ:** ความเข้ากันได้ที่รับรองมีผลจริงและไม่ยอมรับทุกรุ่นโดยไม่มีขอบเขต
หากขั้นใดยังไม่มี implementation หรือยังไม่ได้ตรวจ ให้บันทึก `not_run` ไม่ใช่ `passed`

## ชุดหลักฐานและการสรุปผล

เก็บหลักฐานแต่ละรุ่น/session แยกกัน ประกอบด้วย:

| หลักฐาน | ข้อมูลขั้นต่ำ |
| --- | --- |
| สภาพแวดล้อม | รุ่นโปรเจกต์/commit, Python, runtime, เวลา UTC, ZIP hash |
| ข้อมูลเข้า | CSV ต้นทางและ hash, expected/fixture lock ที่ใช้ |
| ผลตรวจ | จำนวน baseline/new tests จริง, ผลครบ 100 ใบ, failures/errors/skipped, stdout/stderr |
| รายงาน | summary/details/source, receipt, hash/ขนาดของแต่ละไฟล์ |
| กู้คืน | snapshot ก่อน/หลัง, attempts/history, controller PID/log/หลักฐานหยุด |
| backup | ZIP/hash, การยืนยันรับไฟล์จริง, ผลคืนใน runtime ใหม่ |
| patch compatibility | รุ่นต้นทาง/ปลายทาง, ผลอ่าน/เปิดต่อ, หลักฐานว่าผลเก่าไม่เปลี่ยน |

เริ่มสถานะหลักฐานเป็น `not_run` ใช้ `passed` เฉพาะข้อที่มีผลจริงและไฟล์ตรวจกลับได้
ข้อที่ล้มให้เก็บผลจริงกับเหตุผล ไม่แก้คำตอบอ้างอิงเพื่อให้ตรงผลที่ได้
`colab_acceptance_complete` ต้องอิงการตรวจครบและหลักฐานที่ตรวจทานแล้ว
การอนุมัติ release หรือค่า `release_ready` ไม่เปลี่ยน Colab จาก false เป็น true โดยอัตโนมัติ
